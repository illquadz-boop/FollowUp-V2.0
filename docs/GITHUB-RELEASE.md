# GitHub v2.0 업로드 절차

대상 저장소가 확인된 뒤 수행하는 절차입니다. 이 문서나 로컬 ZIP이 존재한다고 GitHub 업로드가 완료된 것은 아닙니다.

## 버전 규칙

- npm 패키지 버전: `2.0.0`
- Git 태그: `v2.0`
- GitHub Release 제목: `FollowUp v2.0 — 프론트엔드 및 백엔드 통합 가이드`
- 릴리스 설명: `docs/releases/v2.0.md`
- 소스 ZIP 권장 이름: `FollowUp-v2.0-source.zip`

## 업로드 전 확인

1. 정확한 GitHub 계정·저장소 URL·공개 범위를 확인합니다.
2. 해당 저장소에 코드를 쓸 수 있는 계정으로 Git 인증을 준비합니다.
3. 저장소의 기존 파일·기본 브랜치·`v2.0` 태그 존재 여부를 확인합니다.
4. 기존 코드가 있다면 별도 작업 브랜치에서 검토하고 PR로 반영합니다. 기존 기본 브랜치를 강제로 덮어쓰지 않습니다.
5. `.env.local`, API 키, DB 비밀번호, 실제 사용자 데이터가 커밋 대상에 없는지 확인합니다.
6. `npm ci`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`를 수행합니다.

## 소스 배포 원칙

- 코드·원본 로고·테스트·문서·패키지 잠금 파일을 포함합니다.
- `node_modules`, `.git`, 빌드 결과, 개발 서버 상태, 로컬 환경변수, 자격 증명은 소스 ZIP에서 제외합니다.
- `.env.example`에는 공개 가능한 설정 예시만 포함합니다.
- `.openai/hosting.json`은 기존 Sites 프로젝트의 연결 메타데이터이며 비밀키는 아닙니다. 이 파일이 GitHub 쓰기 권한이나 Sites 소유 권한을 제공하지 않습니다. 포크한 프로젝트에서 기존 사이트로 재배포하지 마세요.
- 일반 정적 배포에서는 `dist/client` 결과물을 사용합니다. GitHub Pages의 저장소 하위 경로 배포는 현재 루트 기준 자산 경로와 추가 조정이 필요할 수 있습니다. GitHub에 코드 업로드만으로 사이트가 실행되는 것은 아닙니다.

## 빈 원격 저장소에 게시할 때

다음은 Git 인증이 준비되고, 원격 저장소가 비어 있으며, 로컬 `main`과 `v2.0`이 검증된 경우의 예시입니다. URL 자리에는 확인한 실제 주소를 사용하세요. 이미 등록된 원격 이름을 덮어쓰지 않도록 먼저 확인합니다.

```sh
git remote -v
git remote add github <확인한-GitHub-저장소-URL>
git push github main
git push github refs/tags/v2.0
```

`v2.0`이 원격에 이미 존재하면 강제 이동하지 말고 기존 태그 내용을 확인한 뒤 사용자와 버전 정책을 정합니다. 저장소에 기존 코드가 있으면 위 명령을 그대로 실행하지 말고 기존 이력에 맞춰 통합하세요.

## GitHub Release 작성

1. 코드와 `v2.0` 태그가 GitHub에서 확인되는지 확인합니다.
2. 저장소의 Releases에서 새 릴리스를 작성합니다.
3. 태그로 `v2.0`을 선택합니다.
4. 제목과 `docs/releases/v2.0.md` 내용을 입력합니다.
5. 소스 ZIP을 첨부하려면 태그가 가리키는 동일 커밋에서 만든 ZIP을 사용합니다.
6. 저장소 공개 범위와 릴리스 내용을 확인한 뒤 게시합니다.

태그만 올리는 것과 GitHub Release 페이지를 만드는 것은 별개입니다. 두 작업의 완료 여부를 각각 확인하세요. 백엔드가 아직 구현되지 않았다는 안내를 릴리스 설명에서 제거하지 마세요.
