# 실제 백엔드 연동 — 2026-09-10

명세: http://13.124.207.246:8080/v3/api-docs (FollowUp API v1)

## 실행

Node.js 22.13 이상에서 `npm ci`, `npm run dev`로 실행합니다. 기본은 실제 API 모드입니다. 데모를 원하면 `.env.local`에 `VITE_DATA_MODE=demo`를 설정하고 재시작합니다.

브라우저는 같은 출처의 `/api`에 요청하고 `app/api/[...path]/route.ts`가 Spring Boot API로 전달합니다. 따라서 현재 결과물은 **서버 실행이 필요한 빌드**이며 `dist/client`만 정적 호스팅하면 API가 동작하지 않습니다. 별도 Vite 프록시 설정은 필요하지 않습니다.

서버의 `FOLLOWUP_BACKEND_URL` 환경변수로 백엔드를 지정합니다. 기본값은 위 IP입니다. `VITE_API_BASE_URL`은 새 연결 계층에서 사용하지 않으며 브라우저는 의도적으로 `/api`만 호출합니다. EC2 주소가 바뀌면 서버 환경변수를 변경하세요. 운영 환경에서는 백엔드 HTTPS 주소로 변경해야 서버 간 토큰·데이터 전송도 암호화됩니다. 브라우저↔프론트 서버의 HTTPS 중계가 EC2까지의 HTTP 구간을 암호화해주지는 않습니다.

## 구조

- `lib/swagger-api.ts`: 실제 Swagger 응답 스키마, 모든 API 요청. 목록과 상세 DTO를 분리합니다.
- `lib/backend-proxy.ts`: 고정된 백엔드로만 전달하는 경로·메서드 허용 목록, 로그인 토큰의 HttpOnly 쿠키 보관, 동일 출처 쓰기 검사.
- `app/api-app.tsx`: 실제 인증, 프로젝트, 멤버, 대시보드, 업무 카드와 상세 수정.
- `app/api-meetings.tsx`: 회의 작성·상세·수정, 분석 요청·상태 조회·검토·확정.
- 기존 `lib/api.ts`의 `createHttpRepository`는 과거 계약 호환 테스트용으로 남아 있습니다. 실제 API 모드 화면은 `backend`를 사용합니다. 기존 데모 화면은 유지됩니다.

## 인증

백엔드의 Bearer 토큰은 브라우저 JSON이나 localStorage에 저장하지 않습니다. 프론트 서버가 `/api` 경로의 HttpOnly·SameSite=Lax 쿠키로 설정하고 HTTPS에서는 Secure 속성을 사용합니다. 브라우저를 새로고침해도 쿠키가 있으면 `/api/auth/session`에서 백엔드의 내 프로젝트 조회를 통해 인증을 확인합니다.

`/api/auth/session`, `/api/auth/logout`은 프론트 중계 서버가 제공하는 경로이며 Swagger에 추가된 백엔드 기능이 아닙니다. 로그아웃은 이 브라우저의 쿠키를 지웁니다. 서버 토큰 폐기·재발급 API는 없으므로 만료 시 다시 로그인합니다. 만료 시간 단위가 명세에 없어서 `expiresIn`을 추측하지 않고 백엔드의 인증 결과를 따릅니다. 사용자 ID나 이름을 토큰에서 추측하지 않습니다. 프로젝트 권한 검사는 백엔드가 수행합니다.

## 화면에서 연결된 기능

회원가입, 로그인/로그아웃, 내 프로젝트 목록/생성/상세/수정/삭제, 이메일 멤버 추가/조회/제거, 회의 생성/목록/상세/수정/삭제, 참여자와 이전 업무 연결, 텍스트 파일 불러오기, AI 요청/조회/폴링/검토/확정, 업무 생성/목록/상세/수정/삭제/드래그 상태 변경/필터, 원본 회의 링크, 서버 대시보드입니다.

업무 목록에 원본 회의 ID가 없어 화면에 보이는 카드의 상세를 추가 조회하고 캐시합니다. 상·하단 번호는 No.1부터 표시합니다. 카드 수가 많아지면 백엔드 목록에 originMeetingId를 추가하면 요청 수를 줄일 수 있습니다.

회의 일시는 현재 서버 응답처럼 시간대 없는 팀 기준 일시로 입력·전송합니다. 시간대 변환을 임의로 하지 않습니다. 대시보드 완료율은 doneCount/totalCount로 계산하여 completionRate 단위를 추측하지 않습니다.

## 명세에 없어 제외한 기능

워크스페이스, 전체 사용자 검색, 프로필 수정, 별도 일정 배열, 수정한 AI 초안의 서버 임시 저장, 수동 업무의 회의 연결 변경·추천 이유 변경입니다. 분석 요청은 기존 결과를 재사용할 수 있으므로 ‘기존 결과 열기’로도 사용합니다. 분석 ID는 URL의 analysis 검색 매개변수에 유지되어 새로고침 후 조회됩니다. 회의별 최신 분석 GET이 없어, ID를 모르는 상태에서는 사용자가 분석 시작·기존 결과 열기 버튼을 누릅니다. 확정 전 수정한 초안은 메모리 상태이며 다른 기기와 공유되지 않습니다.

## 실제 서버 검증 결과

로컬 중계 경로를 통해 실제 EC2/RDS API에 요청했습니다. 두 번째 검증 실행은 40개 요청 검사를 마쳤습니다. 그중 참여자 PATCH 500은 **성공한 기능이 아니라 재현된 백엔드 결함**입니다. 삭제 제한·중복 확정의 409는 명세대로 확인했습니다.

- 가입·로그인·로그인 복원·로그아웃 정상.
- 프로젝트 생성·목록·상세·수정·삭제 정상.
- 이메일 멤버 추가·목록·제거 정상.
- 회의 생성·목록·상세 정상. 제목·원문·일시 PATCH는 정상.
- 업무 생성·상세·상태 변경·조회·삭제 정상.
- AI 분석 GENERATED → 검토 입력 확정 CONFIRMED → 실제 업무 1건 생성 확인. 생성 업무의 originMeetingId 확인.
- 같은 분석 재확정 409, 업무 수 1건 유지 확인.
- 대시보드 스키마 확인. 분석 이력이 있는 회의 삭제 409 확인.

### 백엔드 수정이 필요한 두 항목

1. **회의 참여자 변경 500**: `PATCH /api/meeting/{id}`에서 `participantIds`를 보내면 Internal server error. 제목·내용·일시만 보내면 정상입니다. 프론트는 참여자 선택이 바뀌지 않았다면 해당 필드를 제외해 일반 수정을 정상 처리합니다. 실제 참여자 변경은 서버 수정 전까지 실패하며 입력을 유지하고 사유를 표시합니다.
2. **업무 값 해제 미반영**: `PATCH /api/action-item/{id}`에 `assigneeUserId: null`, `dueDate: null`을 보내면 200이지만 기존 값이 유지됩니다. 프론트는 응답을 비교하여 성공으로 표시하지 않습니다. 백엔드는 PATCH의 필드 생략과 명시적 null을 구분해야 합니다.

위 두 문제는 프론트만으로 정상 저장을 보장할 수 없습니다. 해당 서버 코드가 수정되면 동일한 프론트 요청으로 다시 검증할 수 있습니다.

### 테스트 데이터

테스트 전용 계정 4개(`followup-test-*`, `followup-member-*`, 도메인 example.invalid)를 생성했습니다. 계정 삭제 API가 없어 계정은 남습니다. 첫 실행이 회의 PATCH에서 중단되어 프로젝트 2/회의 1/업무 1이 남았습니다. 두 번째 실행의 일반 CRUD 데이터(프로젝트 3)는 삭제했습니다. 분석 이력 삭제 제한으로 AI 검증 프로젝트 4/회의 3/분석 1/업무 3은 남겨두었습니다. 사용자 기존 데이터는 변경하지 않았습니다. 비밀번호·토큰은 로그나 저장소에 남기지 않았습니다.
