# TIL — FollowUp v2.0

**학습일:** 2026-09-09  
**주제:** 회의록 기반 후속 업무 관리 프론트엔드 구현

## 📝 오늘 배운 내용 요약

1. **화면과 데이터 로직을 분리하는 방법**

   - 화면 컴포넌트가 직접 저장 방식에 의존하지 않도록 `Repository` 인터페이스를 만들었다.
   - 데모 모드에서는 브라우저 로컬 저장소를 사용하고, API 모드에서는 Axios 기반 HTTP 저장소로 교체할 수 있게 구성했다.

2. **회의 분석 결과를 안전하게 확정하는 흐름**

   - 회의 상태를 `DRAFT → REVIEW → CONFIRMED`로 나누었다.
   - AI 분석은 초안을 만드는 단계이고, 사용자가 결정 사항·일정·업무를 검토한 뒤 확정하도록 분리했다.

3. **프론트엔드와 백엔드 사이의 계약 설계**

   - Zod 스키마로 폼 입력과 API 응답을 검증했다.
   - 담당자, 마감일, 우선순위처럼 업무 생성에 필요한 값은 백엔드에서도 다시 검증해야 한다는 점을 정리했다.

4. **중복 확정과 캐시 문제를 예방하는 방법**

   - 회의 확정 요청에 `Idempotency-Key`를 사용해 같은 초안이 여러 번 업무로 생성되지 않도록 했다.
   - React Query 키에 사용자 ID와 프로젝트 ID를 포함해 사용자 전환 시 이전 데이터가 섞이지 않도록 했다.

## 💭 오늘의 회고

회의록을 단순히 보여주는 화면보다, 회의에서 나온 결정과 업무가 실제 실행으로 이어지는 흐름을 설계하는 일이 더 중요했다. 특히 “분석 완료”와 “업무 확정”을 하나의 동작으로 처리하지 않고 검토 단계를 둔 덕분에 자동화의 편리함과 사용자의 통제권을 함께 확보할 수 있었다.

## **배운 점**

1. **UI 완성도와 데이터 정합성은 함께 설계해야 한다.**

   애플 홈페이지처럼 직관적인 화면과 모션을 구현하는 것만으로는 충분하지 않았다. 로딩·오류·빈 상태·중복 제출·삭제 확인까지 포함해야 실제 사용 가능한 제품 경험이 된다.

2. **프론트엔드의 타입은 백엔드 계약을 구체화하는 도구다.**

   `Meeting`, `Draft`, `Task`의 구조와 상태를 타입·스키마로 명확히 정의하니 화면 간 데이터 흐름과 API 응답의 누락을 빠르게 확인할 수 있었다.

3. **AI 결과는 항상 사람이 검토할 수 있어야 한다.**

   담당자나 날짜를 확신할 수 없는 경우에는 임의의 값을 채우기보다 비워 둔 뒤 사용자가 수정하도록 설계하는 편이 안전하다.

4. **보안 책임은 브라우저에 둘 수 없다.**

   API 키는 프론트엔드에 넣지 않고 서버에서 AI를 호출해야 한다. 세션·CSRF·권한·중복 확정 검사는 화면이 아니라 백엔드가 최종 책임을 가져야 한다.

## **어려운 점/개선할 점**

1. **데모 저장소와 실제 API 저장소의 동작을 맞추는 일이 어려웠다.**

   두 모드가 같은 `Repository` 계약을 구현하도록 만들었지만, 실제 서버가 연결되면 페이지네이션·권한 오류·네트워크 재시도 정책을 추가로 검증해야 한다.

2. **회의 상태와 업무 생성 시점을 명확히 구분해야 했다.**

   분석을 다시 실행하면 기존 초안을 덮어쓸 수 있지만, 이미 확정된 회의의 업무를 중복 생성해서는 안 된다. 백엔드에서는 트랜잭션, 초안 버전, 고유 제약 조건을 함께 적용해야 한다.

3. **날짜와 시간의 기준을 더 엄격하게 다뤄야 한다.**

   마감일은 `YYYY-MM-DD` 날짜로, 생성·수정 시각은 ISO timestamp로 분리했다. 실제 다국가 서비스에서는 사용자 시간대와 서머타임까지 포함한 테스트가 필요하다.

4. **현재 구현은 프론트엔드 중심이다.**

   데모 모드의 기능 검증은 완료했지만, Spring Boot·MySQL·실제 AI 서버가 연결된 상태의 통합 테스트와 운영 모니터링은 다음 단계의 과제다.

## **액션 플랜**

1. Spring Boot에서 `auth`, `workspace`, `project`, `meeting`, `analysis`, `task` API를 API 계약 문서에 맞춰 구현한다.
2. MySQL 스키마에 사용자·프로젝트 범위, 회의 상태, 초안 버전, 업무 확정 이력에 대한 제약 조건을 추가한다.
3. 세션 인증, CSRF 토큰, CORS, 쿠키 보안 속성을 로컬과 운영 환경에서 각각 검증한다.
4. AI 호출을 서버로 이동하고, 구조화된 JSON 결과 검증과 실패 시 재시도·수동 수정 흐름을 추가한다.
5. 회의 확정 API에 트랜잭션과 `Idempotency-Key` 저장 정책을 적용한다.
6. 프론트엔드에는 실제 API 계약 기반의 통합 테스트와 권한별 E2E 테스트를 추가한다.

## **함께 나누고 싶은 점**

AI 기능을 제품에 넣을 때 가장 중요한 것은 “얼마나 그럴듯하게 생성하는가”만이 아니라 “사용자가 결과를 얼마나 쉽게 확인하고 되돌릴 수 있는가”라고 느꼈다. 자동화의 마지막 단계에 사람의 검토와 확정 버튼을 남겨 두면, 결과에 대한 신뢰와 책임 범위를 더 분명하게 만들 수 있다.
